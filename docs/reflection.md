## Reflection

### OOP concepts applied

Building the Microfinance Loan Tracker gave me a real reason to use the OOP ideas from lectures 6 to 10, instead of just recognising them on a slide. Inheritance and generalisation/specialisation (Lecture 6) shaped the domain model directly, `Loan` is an abstract class holding what every loan has in common (principal, interest rate, term, borrower), and `MicroLoan` and `GroupLoan` specialise it, with `GroupLoan` adding a group size that a Micro loan doesn't need. Dynamic polymorphism (Lecture 7) shows up wherever the code calls a method on a `Loan` reference and lets the actual subclass's behaviour run, rather than branching on loan type by hand. The `RiskAssessable` trait (Lecture 8) is a small, focused interface the Dashboard depends on, without caring which concrete type implements it, which is the point of using a trait instead of just inheriting concrete behaviour. Parametric polymorphism (Lecture 10) shows up in `Repository[T]` and the abstract `CsvStore[T]`, one generic repository and one generic CSV read/write shape, reused for both `Borrower` and `Loan` instead of writing the same storage logic twice.

### Problems faced

Most of my real problems weren't in the domain model, they were in ScalaFX. The Borrower field on the Disburse Loan screen took by far the most debugging, making a `ComboBox` both typeable and selectable meant learning that an editable ComboBox isn't one styled control but an inner `TextField` and a separate arrow-button glued together, and CSS that looked correct on paper still made the whole box disappear at one point, because I'd made both the outer control and its inner TextField transparent at the same time. I also hit a string of compile errors from mixing raw JavaFX types (`ComboBox.converter`, `ComboBox.editor`) with ScalaFX's wrapped versions, which needed `scalafx.Includes` imported to resolve. Later, matching S2-6's required `onAction = handle { ... }` idiom directly conflicted with a clean `-Wunused` compile, since `handle` is deprecated in the ScalaFX version this project pins, and using it produces a warning; I solved that with a narrowly scoped `@nowarn` rather than silencing warnings project-wide.

### Strengths and weaknesses

My strength going into this was the domain side, the immutable case classes, the `Either`-based validation, and the CSV persistence layer came together without much struggle, largely because I understood what each OOP concept from lecture was actually for before I used it. My weakness was ScalaFX layout and CSS specifically, I spent far more time getting one field to look and behave correctly than I expected to, and only later switched to a more reliable approach, reusing an existing style class instead of reconstructing one from scratch, once I recognised the incremental approach wasn't converging. If I did this again, I'd settle the shared styling for all input fields before building each screen individually, rather than adjusting one screen's look after the fact and chasing consistency between screens afterwards.
